# StackGPT — community verification layer for AI answers (PoC)

## What this is
A browser extension + backend that, for a ChatGPT answer, finds similar previously-solved
technical problems and shows community evidence (worked / partial / failed reports,
environment breakdown, trust status). Not a chatbot, not an LLM. Pilot domains:
programming and consumer electronics.

## PoC scope (must support)
1. ChatGPT answer detection
2. Extraction of answer text and code blocks
3. Semantic retrieval of similar problems/solutions
4. Context-aware solution matching
5. Community validation and voting
6. Evidence display via browser extension

## Architecture
```
chatgpt.com content script (ChatGptAdapter) -> background service worker -> Java API -> Postgres+pgvector
```

### Monorepo layout
```
/extension   WXT + TypeScript + Preact, Manifest V3
/api         Java 21, Spring Boot 3, JdbcTemplate, Flyway, Maven
/db          seed data (JSON/CSV) + seeding scripts
docker-compose.yml   pgvector/pgvector:pg16 + api
```

### Extension
- Content script on https://chatgpt.com/*. One debounced MutationObserver.
- DOM contract (keep ALL selectors in one ChatGptAdapter file):
  - message el: `[data-message-author-role="user|assistant"]`, keyed by `data-message-id`
  - real assistant answers have `data-message-model-slug`; skip assistant els without it
    (transient "Thinking" pseudo-message)
  - answer content: `.markdown` inside the message el (churns while streaming)
- Answer is "done" when text stable ~1.5s AND stop-generation button absent.
- Pair each answer with the preceding user message (the question = problem description).
- Extraction: prose (code removed), codeBlocks[] {lang from `language-*`, code, isShell},
  steps[] from ordered lists.
- Privacy: send to backend only when user clicks "Check" (or per-site opt-in). Never auto-upload.
- UI: badge under answer -> expandable evidence panel, rendered in Shadow DOM
  (WXT createShadowRootUi). Buttons: worked / didn't work / add context.
- Content script never calls the API; background service worker does (auth, caching, CORS).
- Future: ClaudeAdapter etc. — design adapters behind a common interface.

### Backend pipeline (`POST /v1/verify`)
1. ProblemExtractor (rules/regex for PoC, LLM later behind interface): normalized problem
   statement, error signatures (e.g. `ModuleNotFoundError: ...`, `ERR_CONNECTION_RESET`),
   env facets JSON `{os, lang, pkg:{name:ver}, device}`.
2. Embedder interface. Default: LOCAL in-process ONNX model (bge-small-en-v1.5 or
   all-MiniLM-L6-v2, 384-dim) via LangChain4j. Alt impl: OpenAI text-embedding-3-small.
3. Retriever: hybrid search in Postgres — pgvector HNSW (cosine) top-50 + tsvector/GIN
   full-text top-50 + exact error-signature match list, fused with RRF
   score = sum 1/(60 + rank).
4. ContextMatcher: hard conflicts (OS-specific fix on other OS, model-specific fix on other
   device) drop/flag; soft rerank by facet overlap + version distance.
5. SolutionAligner: embed AI answer steps+code, compare to stored solutions of matched
   problem -> "matches solution S" / "partial overlap" / "novel (no evidence)".
6. TrustScorer:
   - verified: Wilson lower bound of success rate >= 0.7, >= N independent reporters, recent
   - conflicting: outcomes diverge across env segments
   - outdated: no recent successes / recent failures (time decay)
   - partial / unverified otherwise

### API
- POST /v1/verify     {platform, question, answer{prose, codeBlocks, steps}, envHints}
                      -> {matches[], alignment, trustStatus, evidence}
- POST /v1/attempts   {solutionId, outcome: worked|partial|failed, env, note}  (1 per user per solution)
- POST /v1/votes      {solutionId, helpful: bool}   (helpfulness kept separate from outcome)
- POST /v1/solutions  (submit alternative)
- POST /v1/flags      {solutionId, kind: outdated|misleading}
- GET  /v1/solutions/{id}
- PoC auth: simple anonymous user token generated by extension.

### Data model (Postgres)
problems(id, title, body, error_sigs text[], env jsonb, embedding vector(384), fts tsvector generated, created_at)
solutions(id, problem_id, body, steps jsonb, code text, embedding vector(384), created_at)
attempts(id, solution_id, user_id, outcome, env jsonb, note, created_at)  unique(solution_id,user_id)
votes(solution_id, user_id, helpful)  pk(solution_id,user_id)
flags(id, solution_id, user_id, kind, created_at)
users(id, token, created_at)
Indexes: HNSW vector_cosine_ops on embeddings, GIN on fts, GIN on error_sigs and env.

### Cold start / seed
- Programming: Stack Exchange content (CC BY-SA, attribution required; verify current
  data-dump access terms). Accepted answers + scores = labelled weak proxy evidence.
- Consumer electronics: 50–100 hand-curated problems + CLEARLY LABELLED synthetic attempts.

## Build order
1. docker-compose + schema (Flyway) + seed
2. /v1/verify with hybrid retrieval only
3. Extension: detect, extract, raw panel
4. ContextMatcher + SolutionAligner
5. Votes/attempts + TrustScorer
6. Polished panel + end-to-end demo script

## Conventions (owner preferences)
- Java for backend. Compact, minimal variable names. Clean, simple structure.
- State time/space complexity for non-trivial algorithms (in comments/docs).
- Tests: concrete cases with expected vs actual. Add unit tests for extractor, RRF fusion,
  context matcher, trust scorer; a fixture-HTML test for the ChatGPT adapter.
- Keep each step runnable before moving on; commit after each build-order step.
